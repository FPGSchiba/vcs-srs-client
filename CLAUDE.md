This file orients every Claude Code session that opens this repo. Read it before doing anything else.

## What this project is

The **Vanguard Communications System (VCS) client** — a desktop voice-comms application for the Star Citizen community using the SRS-style radio paradigm. Multi-window, distributed-voice-aware, cross-platform (Windows / macOS / Linux). Stack:

- **Frontend:** Wails v3 + React 18 + TypeScript + Vite + Tailwind + shadcn/ui + Zustand + TanStack Query/Router. Per-window Vite entries (one bundle per OS window).
- **Backend:** Go (`github.com/FPGSchiba/vcs-srs-client`), `log/slog` logger, `google.golang.org/grpc` for control, custom UDP for voice (Phase 5+), `malgo` for audio (Phase 4+).
- **Wire contract:** `srs.proto` at repo root. Bindings generated into `srspb/` (gitignored, regenerated by CI).

Foundational decisions are locked in the design spec — **do not re-litigate the tech stack** in new sessions. If something needs to change, update the spec and surface it to the user before touching code.

Joystick input is deliberately **Windows + Linux only**. macOS reports "unsupported": Star Citizen has no macOS build, so there is no coexistence problem to solve there, and wiring `IOHIDManager` would require negotiating a second TCC permission (Input Monitoring) distinct from the Accessibility grant the keyboard hotkey path already asks for — not worth the privacy prompt for a platform the target game doesn't run on.

### Login: guest-only, by decision

Guest login is the **only** supported sign-in path until Phase 2 resumes. The SSO button in `frontend/src/windows/main/screens/Welcome.tsx` is rendered `disabled` on purpose — it is a placeholder, not an oversight. **Do not remove it, do not restructure the two-stage welcome UX around its absence, and do not build an alternative account-login path to work around it.** The screen stays exactly as the design prototype specifies so that re-enabling SSO later is a wiring job, not a redesign.

The guest path is fully wired and verified against the server: `Welcome.tsx` → `App.Connect` → `session.Connect` → `InitAuth` → `GuestLogin` → `SyncClient` → `SubscribeToUpdates`. The server ships `enableGuestAuth: true` / `enablePluginAuth: false` by default, so no server change is needed for it.

Password handling looks odd but is correct — do not "fix" it without reading both sides. The client bcrypt-hashes the typed password and sends the hash; the server calls `CheckPasswordHash(request.Password, coalition.Password)`, i.e. `bcrypt.CompareHashAndPassword(clientHash, storedPlaintext)`. That verifies iff the typed password equals the coalition's configured password. See `vngd-srs-server/srs/auth_service.go` and `utils/general.go`.

### Voice codec geometry is a wire contract — do not change unilaterally

Opus is configured **48 kHz / 20 ms (960 samples) / mono / `Application.Audio` / 48 kbps / FEC off / DTX off** in `internal/voice`. This is not a tunable — the C# peer (`VNGD-SimpleRadioStandalone`) normalises every decoded frame to exactly 960 samples and silently truncates or zero-pads anything else, with nothing logged to explain the resulting chopped or padded audio. Changing any of these values without first confirming the C# peer's decoder expects the same geometry will desync audio between clients in a way neither side's logs will surface. Treat any proposed change here the same as a proto change: propose it and get explicit approval before touching it.

### Control-plane TLS (Phase 7.1, closes spec risk R5)

`internal/session/dial.go` picks transport by address and one config key, `tls_ca_file`: `tls_ca_file` set → TLS pinned to that CA for **any** host (loopback included); else a loopback host (`localhost` / `127.*` / `::1`) → insecure; else → TLS via the OS trust store. There is no plaintext escape hatch for a remote host, and no fallback to plaintext when a handshake fails — Phase 1's fail-closed rule inverted rather than relaxed (a remote host used to be refused outright; it is now required to be encrypted). An unreadable or certificate-free `tls_ca_file` is an error, never a silent fall-through to system roots. The dial is bounded by a 10s `dialTimeout` so a persistent handshake failure returns instead of hanging — this bounds the dial only; `internal/app/bindings.go` calls the post-dial auth sequence (`InitAuth` etc.) with `context.Background()`, so a server that completes TLS and then never answers still hangs the Welcome screen forever. Three failures get actionable diagnostic text: the server not speaking TLS ("no clientTLS block configured"), a certificate not trusted, and a hostname mismatch.

The server side needs its own `clientTLS` config block or the connection fails with the "not speaking TLS" diagnosis: omitting the block serves plaintext plus a startup WARN; setting only one of `certificateFile`/`privateKeyFile` leaves the client-facing gRPC port down (the process itself keeps running and the admin HTTP port is unaffected) with an error naming the missing field; setting both with the files absent generates a self-signed pair once and reuses it on later starts.

**Correction, 2026-09-28:** earlier revisions of this file claimed "the deployed server already has certs." That was true but misleading — those certificates serve the server-to-server VoiceControl channel on port 14448, not the client-facing port this client dials. The client-facing gRPC listener (`clientGrpcServer`, registering `SRSService`/`AuthService`) had no TLS option at all until `vngd-srs-server` branch `feat/client-port-tls`. This false belief is why the client-facing port stayed unencrypted for six phases — recorded here rather than silently deleted so a future reader can see the trap.

### The notification channel (Phase 7.2)

`internal/notify` is a pure, source-agnostic package (`Post`/`Raise`/`Resolve`/`MarkRead`/`Dismiss`/`Clear`) that hotkeys, joystick and audio all route through. Two things a future session would otherwise get wrong:

- **The level-to-edge contract is the consumer's job, not the emitter's.** `hotkeys:state` has no dedupe at its emit site at all and fires from nine call sites — rebinding nineteen actions emits ~38 identical payloads. `audio:state` compares a struct containing monotonic xrun counters and fires every ~2s during a glitch. Anything consuming either event through the notification channel must project the payload down to the user-visible fields and rely on `internal/notify`'s fingerprint (computed over what the user can see) to collapse the noise. **Do not "fix" the chatty emitters** — every other consumer of those events is already idempotent against the current emission rate, and de-chattying the emit site would be an unreviewed behaviour change to code outside this phase's scope.
- **The notification sound ships silent by missing asset, not missing code.** `notify_alert.wav` is the tenth outstanding WAV file (joining Phase 4's original nine SFX slots). Do not synthesise a placeholder tone — `internal/audio/assets/README.md` records the pack as a blocking dependency on the user, "not something to substitute." The playback path (`PlayNotification` → the notification voice pool → the mixer's notification bus) is unit-tested and wired end to end; only the sample is missing.

### gopls is unreliable in this repo — widen your suspicion, not just "undefined symbol"

Earlier phases recorded gopls reporting existing symbols as undefined. Phase 7.2 hit **twelve** false positives across **three distinct kinds**, not just that one: "symbol undefined", `"log/slog" imported and not used`, and `cannot use generic function slices.Equal without instantiation`. The latter two would be hard compile errors if real — they are not: every single instance was contradicted by a clean `go vet`. Treat any gopls diagnostic in this repo as unverified until `go build`/`go vet` confirms it; never act on it on its own.
