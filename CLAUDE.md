## What this project is

The **Vanguard Communications System (VCS) client** — a desktop voice-comms application for the Star Citizen community using the SRS-style radio paradigm. Multi-window, distributed-voice-aware, cross-platform (Windows / macOS / Linux). Stack:

- **Frontend:** Wails v3 + React 18 + TypeScript + Vite + Tailwind + shadcn/ui + Zustand + TanStack Query/Router. Per-window Vite entries (one bundle per OS window).
- **Backend:** Go (`github.com/FPGSchiba/vcs-srs-client`), `log/slog` logger, `google.golang.org/grpc` for control, custom UDP for voice (Phase 5+), `malgo` for audio (Phase 4+).
- **Wire contract:** `srs.proto` at repo root. Bindings generated into `srspb/` (gitignored, regenerated by CI).

Foundational decisions are locked in the design spec — **do not re-litigate the tech stack** in new sessions. If something needs to change, update the spec and surface it to the user before touching code.

## Mandatory workflow — starting any new phase

> **When the user says any of: "let's start Phase N", "begin the next phase", "pick up Phase N", "let's do Phase N", or any equivalent — you MUST invoke the `superpowers:brainstorming` skill before writing any code, scaffolding, or implementation plan.**

This is non-negotiable. Each phase gets its own design doc derived from the master spec before implementation. The brainstorming flow will:

1. Read the master design spec and the relevant `ROADMAP.md` row.
2. Ask clarifying questions and propose 2 – 3 approaches.
3. Present the phase design in sections for approval.
4. Write the phase design doc to `docs/superpowers/specs/YYYY-MM-DD-vcs-client-phase-N-<theme>-design.md`.
5. Commit it.
6. Hand off to `superpowers:writing-plans` only after the user approves the spec.

If `superpowers:brainstorming` is unavailable in the current environment, **stop and report it** rather than skipping the step.

Joystick input is deliberately **Windows + Linux only**. macOS reports "unsupported": Star Citizen has no macOS build, so there is no coexistence problem to solve there, and wiring `IOHIDManager` would require negotiating a second TCC permission (Input Monitoring) distinct from the Accessibility grant the keyboard hotkey path already asks for — not worth the privacy prompt for a platform the target game doesn't run on.

### Login: guest-only, by decision

Guest login is the **only** supported sign-in path until Phase 2 resumes. The SSO button in `frontend/src/windows/main/screens/Welcome.tsx` is rendered `disabled` on purpose — it is a placeholder, not an oversight. **Do not remove it, do not restructure the two-stage welcome UX around its absence, and do not build an alternative account-login path to work around it.** The screen stays exactly as the design prototype specifies so that re-enabling SSO later is a wiring job, not a redesign.

The guest path is fully wired and verified against the server: `Welcome.tsx` → `App.Connect` → `session.Connect` → `InitAuth` → `GuestLogin` → `SyncClient` → `SubscribeToUpdates`. The server ships `enableGuestAuth: true` / `enablePluginAuth: false` by default, so no server change is needed for it.

Password handling looks odd but is correct — do not "fix" it without reading both sides. The client bcrypt-hashes the typed password and sends the hash; the server calls `CheckPasswordHash(request.Password, coalition.Password)`, i.e. `bcrypt.CompareHashAndPassword(clientHash, storedPlaintext)`. That verifies iff the typed password equals the coalition's configured password. See `vngd-srs-server/srs/auth_service.go` and `utils/general.go`.

### Voice codec geometry is a wire contract — do not change unilaterally

Opus is configured **48 kHz / 20 ms (960 samples) / mono / `Application.Audio` / 48 kbps / FEC off / DTX off** in `internal/voice`. This is not a tunable — the C# peer (`VNGD-SimpleRadioStandalone`) normalises every decoded frame to exactly 960 samples and silently truncates or zero-pads anything else, with nothing logged to explain the resulting chopped or padded audio. Changing any of these values without first confirming the C# peer's decoder expects the same geometry will desync audio between clients in a way neither side's logs will surface. Treat any proposed change here the same as a proto change: propose it and get explicit approval before touching it.

### Known gap: no TLS

`internal/session/dial.go` fails closed on any non-localhost host, so the client can currently only reach a **local** server. The deployed server already has certs. TLS is scheduled for Phase 7 (spec risk R5); pull it forward if remote testing becomes necessary.
